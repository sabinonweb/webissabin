C: where things go wrong

A job about finding bugs in core systems means C questions will be about what goes wrong, not syntax. Be able to explain each of these with a small example:

  • Undefined behaviour: signed overflow, strict aliasing, out-of-bounds access, use-after-free, uninitialised reads. Know why the compiler is allowed to delete your null check.
  • Pointers vs arrays, arrays decaying to pointers, sizeof traps.
  • Struct padding and alignment. Integer promotion and signed/unsigned comparisons.
  • volatile (and why it doesn't make code thread-safe), restrict.
  • Stack vs heap, what a function call does to the stack, what malloc does at a high level.
  • Tools: -Wall -Wextra -fsanitize=address,undefined, lldb/gdb, valgrind in a Linux container.

Bug hunt

Each snippet has one real bug. Give yourself five minutes per snippet before opening the answer.

1. An overflow check

int will_overflow(int x) {
    return x + 1 < x;
}
answer

Signed overflow is undefined behaviour, so the compiler may assume x + 1 never wraps. Under that assumption x + 1 < x is always false, and at -O2 the function usually compiles to return 0. Compare against the limit instead: return x == INT_MAX;

2. A greeting

char *greet(const char *name) {
    char buf[64];
    snprintf(buf, sizeof buf, "hi %s", name);
    return buf;
}
answer

buf lives on the stack and is gone when the function returns, so the caller gets a dangling pointer. It often "works" in testing because nothing has overwritten that stack memory yet. Fix it by having the caller pass in a buffer, or by allocating with malloc and documenting who frees it.

3. Every item except the last

unsigned n = get_len();
for (int i = 0; i < n - 1; i++)
    process(items[i]);
answer

When n is 0, n - 1 wraps to UINT_MAX. The comparison also converts i to unsigned, so the loop runs far past the array. Write i + 1 < n, or return early when n == 0.

4. Allocating a list from a network packet

uint32_t count = read_u32(packet);
struct item *items = malloc(count * sizeof *items);
for (uint32_t i = 0; i < count; i++)
    items[i] = read_item(packet);
answer

An attacker controls count. A large value makes count * sizeof *items wrap around to a small number, so malloc returns a tiny buffer and the loop writes past its end. The malloc result isn't checked for NULL either. Use calloc(count, sizeof *items), which checks the multiplication, and put an upper bound on count.

Rust, deeper than the basics

  • Ownership, borrowing, lifetimes. Send and Sync, and what each one promises.
  • When to use Box, Rc, Arc, Cell, RefCell, Mutex.
  • Generics vs trait objects: static vs dynamic dispatch, inlining, code size.
  • unsafe: what it lets you do, which rules still apply (aliasing, valid values), and checking with Miri.
  • FFI: #[repr(C)], extern "C", who frees memory that crosses the boundary.
  • When zero-cost abstractions cost something: bounds checks, clone() in a hot loop, hidden allocations.

Check yourself

Why won't this compile, and what bug is the compiler preventing?

let mut v = vec![1, 2, 3];
let first = &v[0];
v.push(4);
println!("{first}");
answer

push may need to grow the vector, which moves its contents to a new allocation. first would then point at freed memory. The borrow checker refuses a mutable borrow (push) while the shared borrow (first) is still used later. The C++ version of this code compiles and gives you a use-after-free.

Why is Rc<T> not Send, when Arc<T> is?

answer

Rc updates its reference count with ordinary, non-atomic increments. If two threads cloned or dropped it at once, updates could be lost, the count would be wrong, and the value could be freed while still in use. Arc pays for atomic operations so this can't happen.

Inside an unsafe block you create two &mut references to the same value, but you only ever use one at a time. Is that fine?

answer

No. Two live &mut references to the same memory break Rust's aliasing rules, and that's undefined behaviour even if you never use them at the same moment. The compiler optimises on the assumption that a &mut is the only way to reach that memory. Miri reports this; normal tests usually won't.

Performance and hardware

This is the part most candidates are weakest on, and it's the actual job.

  • Memory: cache lines, locality, struct-of-arrays vs array-of-structs, false sharing.
  • CPU: branch prediction, pipelining, the idea behind SIMD, reading compiler output on Godbolt.
  • Concurrency: atomics, memory ordering (Relaxed, Acquire, Release, SeqCst), how a lock-free SPSC ring buffer works, the ABA problem.
  • Measuring: benchmark before and after, profile (cargo flamegraph, Instruments on macOS, perf in a Linux VM), use criterion, account for variance and warm-up.
Interviewers watch for people who optimise without measuring. Always say how you would check that it got faster.

Check yourself

Two threads each increment their own counter, with no sharing. It runs slower than one thread doing both. Why?

struct Counters {
    a: AtomicU64,   // thread 1 only
    b: AtomicU64,   // thread 2 only
}
answer

False sharing. a and b sit on the same cache line, so each write forces the other core to give up its copy of that line, and the line bounces between cores. Put each counter on its own line with #[repr(align(64))], or 128 on Apple M-series chips.

You loop over a large 2D array with for col { for row { sum += a[row][col] } }. Swapping the two loops makes it several times faster. Why?

answer

C and Rust store 2D arrays row by row. Walking down a column jumps a whole row's width in memory at every step, so almost every access misses the cache. Walking along a row uses every byte of each cache line it loads, and the prefetcher can see the pattern coming.

A producer writes data, then sets ready = true. A consumer waits for ready, then reads data. With Relaxed ordering on ready, what can go wrong?

answer

The consumer can see ready == true and still read the old data. Relaxed makes the flag itself atomic but says nothing about when other memory writes become visible, and ARM chips really do reorder this. Use a Release store on the producer side and an Acquire load on the consumer side: everything written before the release is visible after the acquire.

Your benchmark says a loop takes 0 ns. What happened?

answer

The compiler saw the result was never used and deleted the loop. Pass inputs and outputs through std::hint::black_box (criterion does this for you), and check the generated assembly when a number looks too good.

"I profiled it, saw X, changed Y, and it got Z% faster, because W."

Where to prepare

Everything I'd point you to, grouped by topic. Each group puts the one to start with first. Unless marked otherwise, everything here is free.

Problem solving

  • CSES Problem Set: start here. 300 classic problems grouped by topic, a good fit for Rust practice.
  • Competitive Programmer's Handbook (PDF): the theory that goes with CSES, short chapters.
  • Codeforces: timed contests and rated problems. Enter live Div 2 rounds to practise under real pressure.
  • LeetCode and the NeetCode 150 list: interview-style problems, if the online assessment turns out to look like that.
  • USACO Guide: a structured path from easy to hard, with explanations.
  • cp-algorithms: reference for when you need a specific algorithm explained.
  • EbTech/rust-algorithms: shows what competitive Rust looks like (fast input reading, graph templates).

C

  • John Regehr, A Guide to Undefined Behavior in C and C++: start here. Why UB exists and what compilers do with it.
  • Chris Lattner, What Every C Programmer Should Know About Undefined Behavior: the compiler author's side of the same story, in three parts.
  • Modern C by Jens Gustedt: a free book on C as it's written today.
  • Beej's Guide to C: a friendlier refresher if your C is rusty.
  • The Lost Art of Structure Packing: padding and alignment, explained properly.
  • SEI CERT C Coding Standard: a catalogue of real C bug patterns. Good material for the bug-hunt kind of question.
  • cppreference (C section): the reference for what the standard actually says.
  • AddressSanitizer docs and the sanitizers wiki: the tools that find these bugs for you.

Rust

  • Mara Bos, Rust Atomics and Locks: start here. Free online. Atomics, memory ordering, and building your own locks and channels. It covers the ring-buffer build directly.
  • The Rustonomicon: the official guide to unsafe Rust.
  • Learning Rust With Entirely Too Many Linked Lists: ownership, Rc, RefCell and raw pointers, learned by struggling with one data structure.
  • Crust of Rust by Jon Gjengset: long live-coding videos on lifetimes, smart pointers, atomics, channels.
  • The Rust Performance Book: short and practical. Profiling, allocation, bounds checks.
  • The Rust Book and Rustlings: only if a basic topic feels shaky.
  • cheats.rs: a dense cheat sheet to skim the night before.
  • Rust for Rustaceans (paid book): the step after the Rust Book, if you want one book to go deeper.
  • Tools: Miri, loom, criterion, cargo flamegraph, std::sync::atomic docs.

Performance and hardware

  • Algorithms for Modern Hardware (Algorithmica): start here. Caches, branch prediction, SIMD, with real benchmarks. Probably the most useful single link on this page for this job.
  • Denis Bakhvalov, Performance Analysis and Tuning on Modern CPUs: free book on measuring and profiling. His blog, easyperf.net, has practice challenges.
  • Ulrich Drepper, What Every Programmer Should Know About Memory (PDF): the classic. Long; read sections 3 and 6 first.
  • Preshing, Acquire and Release Semantics: the clearest short explanation of memory ordering. Read the posts around it too.
  • Martin Thompson, False Sharing: short, with a benchmark you can reproduce.
  • Why is processing a sorted array faster than an unsorted one?: the famous branch-prediction answer.
  • Brendan Gregg, Flame Graphs: how to read the profiler output you'll be showing in interviews.
  • Agner Fog's optimization manuals: deep reference on CPU internals and instruction costs. Look things up here rather than reading it cover to cover.
  • MIT 6.172, Performance Engineering of Software Systems: a full course with lectures. Pick the lectures on caches, bit hacks and multicore.
  • CMU 15-213 and its textbook CS:APP: the foundations (memory hierarchy, linking, virtual memory). The labs, especially bomb lab and malloc lab, are excellent practice.
  • Casey Muratori, Computer, Enhance! (paid): a performance-aware programming course, if you want guided exercises.
  • Compiler Explorer: check what your code compiles to. Use it constantly.

Real bugs and postmortems

The job is finding bugs in real systems, so read how real ones happened. These also make good interview talking points.

  • Cloudflare, Cloudbleed incident report: an end-of-buffer check written as == instead of >= in a generated C parser leaked private memory into web pages.
  • RustSec advisories: real soundness bugs in Rust crates, many inside unsafe blocks.
  • Google Project Zero blog: detailed write-ups of memory-safety bugs in real software.
  • danluu/post-mortems: a big list of production failures, grouped by cause.
