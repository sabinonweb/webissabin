Ampixa, RustMesh, and an hour of backend

How I'm splitting my days, and how I'm reading Backend from First Principles · 26 Sep 2026

I started with "I don't have time to learn backend." Once I actually counted, that wasn't true. Ampixa takes 3–4 hours a day and the rest of the day is mine. The real problems are that those hours have no structure, and that I can only do about 3–4 hours of real deep work a day before the quality drops. Some of that already goes to Ampixa.

So the decision is: one deep project, one light one.

  • Ampixa is fixed. It's work.
  • RustMesh is the deep project. About half the backend course (concurrency, failure, networking, operations) gets learned inside it, when RustMesh needs that chapter.
  • One hour of backend a day, kept light, for the half RustMesh will never teach me: HTTP, users and auth, databases, caching, web security, scaling.

This is a two-week experiment, not a promise for the next six months. On day 14 I check what actually happened and adjust.

Rules

  • Fixed start times. With a lot of free hours, it's easy to keep pushing things to "later." A block that starts at a set time actually happens.
  • The backend hour stays light. If it turns into building and debugging, it becomes a second deep project and I'm over the limit. Save building for the weekend.
  • Missed a block? Don't double up. Skip it and carry on.
  • The ten-minute rule. If I want to sleep the moment it gets hard, that's usually escaping the difficulty, not being tired. Shrink the task to one paragraph or one function and start that.

How to read a chapter

  1. Predict (5 min). Skim the headings. Write down three questions you think the chapter answers, and your guess at each answer.
  2. Read. Stop at every diagram and redraw it from memory. If you can't, read that part again.
  3. Run and break. Run the Go or Python code. Change one thing on purpose and predict what happens before you run it.
  4. Use it. Backend-hour chapters get built into the side project at the weekend. RustMesh chapters get used in RustMesh, and you write the core logic yourself.
  5. Explain back (5 min). Five lines: what it is, why it exists, one way it fails. If you can't write the "fails" line, you haven't finished the chapter.

Recall

Why is HTTP called stateless if websites remember that I'm logged in?

The protocol doesn't carry memory between requests. Each request stands alone. "Being logged in" is state the application rebuilds on every request from something the client sends again each time: a session cookie that points to server-side state, or a signed token that holds the claims itself.

CORS blocked my request. Is my API now protected from other websites?

No. CORS is enforced by the browser, to stop pages on other origins reading responses. curl, scripts and other servers ignore it. It isn't access control; that has to be auth on the server.

Two transfers read balance = 100 at the same moment, and each takes 80. What happened, and name two fixes.

A lost update: both read before either wrote, so both checks passed. Fixes include locking the row while you read it (SELECT … FOR UPDATE), a conditional update (UPDATE … SET balance = balance - 80 WHERE balance >= 80, then check the affected row count), or optimistic locking with a version column.

Why can a cache make a correct system incorrect?

It's a second copy of the data. Any write that updates the database but not the cache (or does it in the wrong order, or races with a read) leaves the cache serving an old value. You gain speed and take on a consistency problem.

Track 2 · Learned inside RustMesh

Don't read these in order. Read a chapter when RustMesh runs into its problem. The chapter gives you the general idea, and RustMesh is where you use it. Each line has the question that tells you it's time.

CI/CD, one step at a time

Start by reading this site's own .github/workflows/hugo.yaml line by line: what triggers it, what runs, where the output goes. That's already a working pipeline. Then grow RustMesh's pipeline yourself, one step at a time:

  1. On every push: cargo build and cargo test. Fail the PR if they fail.
  2. Add clippy and cargo fmt --check.
  3. Add the multi-node docker compose test.
  4. Build release binaries when you tag a version.

Write the YAML yourself the first time. It's config, but the point is to understand it.

If it falls apart

It will, at least once. When it does, don't redesign this page and don't restart the whole plan. Open it, answer one recall question, and do one backend hour. That's the entire recovery process.
