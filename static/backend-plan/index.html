Learning backend when I "don't have time"

A plan for working through Backend from First Principles · started 25 Sep 2026

The site has 26 chapters. It estimates 2–4 hours each, which comes to roughly 60–70 hours in total. That sounds like a lot until you divide it: at five hours a week it takes about four months. Four months of small, boring, regular sessions will get me further than one heroic weekend followed by six weeks of guilt.

So this page isn't really about backend. It's about three things: when I sit down, what I do in each sitting, and what I build so the reading actually sticks.

The honest time question

"I don't have time" usually means one of two things. Either the week really is full, or the time exists but gets eaten because nothing is scheduled into it. Before planning anything, check which one it is.

For the next three days, write down what you actually did between dinner and sleep, and on the weekend mornings. Don't judge it, just write it down.

If you find 45 spare minutes on most weekdays (you probably will), the plan below works. If you really don't, cut it to the weekend block alone. It will take eight months instead of four, and that's still fine.

The minimum dose

  • 4 weekday sessions × 45 minutes. Same time, same place each day, tied to something that already happens (right after dinner, or before opening Slack in the morning). Reading and running code only. No building.
  • 1 weekend block × 2 hours. This is where you build the week's piece of the project and push it through CI.
  • That's 5 hours a week, about 2 chapters.

Rules that matter more than the schedule:

  • Missed a day? Don't double up. Skip it and carry on. Trying to catch up is how the plan dies.
  • Missed a week? Restart with the recall questions, not with the next chapter.
  • The ten-minute rule. On bad days, promise yourself only ten minutes: one section, one diagram. If you want to sleep the moment it gets hard, that's usually escaping the difficulty, not being tired. Shrink the task until it's small enough to start.

How to read one chapter

Reading a chapter from start to finish and nodding along feels productive, but nothing stays. Each chapter gets the same five steps instead, spread over two or three sessions.

  1. Predict (5 min). Skim the headings only. Write down three questions you think the chapter answers, and your guess at each answer. Being wrong here is what you want: it shows you what to pay attention to.
  2. Read (one session). Read the theory with the diagrams. Stop at every diagram and redraw it on paper without looking. If you can't, read that part again.
  3. Run and break (one session). Run the chapter's Go or Python code. Then change one thing on purpose and predict what happens before you run it. Remove a header, send malformed JSON, kill the database halfway through.
  4. Build (weekend). Add the chapter's idea to your own project (below). You write the core logic yourself. Setup, config and wiring are fine to hand off.
  5. Explain back (5 min). Write five lines in your own words: what the thing is, why it exists, and one way it fails. If you can't write the "fails" line, you haven't finished the chapter.

Put a clock on the reading session so it has an end. Knowing it stops makes it easier to start.

One project, built through the whole plan

Twenty-six separate toy exercises get forgotten. A single project that grows every week doesn't, because each chapter changes something you already built. The suggestion: a tiny wallet API. Accounts, balances, transfers between accounts. Money is useful here because it's unforgiving. Floats lose paisa, a double-submitted request charges someone twice, and two transfers at the same moment can spend the same balance twice. Every chapter has something to protect.

Language: the chapters' code is in Go and Python. Go keeps you close to the reference code and is common in backend jobs. Rust is what you already know and enjoy, but you'll be translating every example. Both are reasonable; pick one and write down why.

Decide what "working" means first

Before each phase, write down how you'll know the phase worked: the checks you'll run, not just "I read it." Some examples of the kinds of checks you could use:

  • Does it run? (curl returns what I expect)
  • Does it match a reference? (the status codes in my API match the chapter's table)
  • Does a failure do what I planned? (kill Postgres mid-transfer and no money disappears)
  • Is it fast enough? (p99 under some number I choose, measured with hey or k6)

You decide which of these matter for each phase. There's a box for it at the top of every phase below.

CI/CD from the first week

CI/CD is chapter 21 on the site, but don't wait that long. You learn it by watching a pipeline grow alongside your code, not by reading about it once.

You already run one. Open .github/workflows/hugo.yaml in this site's repo and read it line by line: what triggers it, what runs, where the output goes. That's CI/CD. Your own site is built and deployed by it.

Then grow the wallet's pipeline one step per phase:

PhasePipeline adds
1On every push: build, run the tests, fail the PR if they fail
2Start a Postgres service container, run integration tests against it
3Linting, go vet/clippy, race detector, a dependency vulnerability scan
4Build a Docker image, push it to a registry, deploy automatically on merge to main

Write the YAML yourself at least the first time. It's config, but the point is to understand it.

The weekly plan

This follows the site's order, with two changes: automated testing (ch 22) is pulled forward into phase 1, and configuration (ch 14) moves next to caching. Every phase ends with a review week. That week is not wasted: it's slack for the weeks that go wrong, and it's where you step back and see the whole picture.

Phase 1 · The request path (weeks 1–6)

Recall, before week 7

Why is HTTP called stateless if websites remember that I'm logged in?

The protocol itself doesn't carry memory between requests. Each request stands alone. "Being logged in" is state the application rebuilds on every request from something the client sends again each time: a session cookie that points to server-side state, or a signed token that holds the claims itself.

CORS blocked my request. Is my API now protected from other websites?

No. CORS is enforced by the browser, to protect the user from pages on other origins reading responses. curl, a script or another server ignore it completely. It isn't access control; that has to be auth on the server.

Authentication vs authorization, in one line each?

Authentication: who are you? Authorization: are you allowed to do this to that? A logged-in user reading someone else's account is an authorization bug, not an authentication bug.

Phase 2 · State & machinery (weeks 7–11)

Recall, before week 12

A client times out on POST /transfers and retries. What can go wrong, and what prevents it?

The first request may have succeeded on the server; only the response was lost. The retry transfers the money a second time. An idempotency key (the client sends a unique key, the server stores the result for that key and returns it on repeats) makes the retry safe.

Why can a cache make a correct system incorrect?

It's a second copy of the data. Any write that updates the database but not the cache (or updates them in the wrong order, or races with a read) leaves the cache serving an old value. Caching gives you speed and costs you a consistency problem.

Phase 3 · Running in production (weeks 12–15)

Recall, before week 16

Two transfers read balance = 100 at the same moment, each takes 80. What happened, and name two fixes.

A lost update: both read before either wrote, so both checks passed. Fixes include locking the row while you read it (SELECT … FOR UPDATE), a conditional update (UPDATE … SET balance = balance - 80 WHERE balance >= 80 and check the affected row count), or optimistic locking with a version column.

Logs, metrics, traces: which one answers "which service made this request slow?"

Traces. Metrics tell you that p99 went up; logs tell you what happened inside one process; a trace follows one request across services and shows where the time went.

If it falls apart

It will, at least once. Work gets busy, a week disappears. When that happens, don't restart the whole plan and don't redesign this page. Open it, answer the last phase's recall questions, and do one 45-minute session. That's the entire recovery process.
